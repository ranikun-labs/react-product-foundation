# 라우팅·인증 가드·API 호출·환경 변수 규약

> 두 제품(Finance, Carelog)의 실제 코드(2026-11 시점)에서 **공통인 부분만 규약**으로, 갈라진 부분은 **선택지**로 적는다.
> RPF는 인증·API 클라이언트·상태관리 라이브러리를 **기본 탑재하지 않는다.** 아래 선택지는 제품이 고르는 항목이며, 어느 쪽도 표준이 아니다.

## 1. 라우팅

### 규약 (두 제품과 RPF 공통)

- 경로 정의의 유일한 원본은 `src/constants/routes.ts`다. 컴포넌트·테스트에 경로 문자열을 하드코딩하지 않는다.
- 공개 웹은 `/:locale/*`, 앱은 `/app/*`(`APP_BASE`)로 나눈다. 루트 `/`는 기본 로케일 redirect 전용이다.
- 지원 로케일은 `SUPPORTED_LOCALES`가 단일 원본이고, 판별은 `isSupportedLocale`만 쓴다.
- 파라미터가 들어가는 경로는 `build*Path()` 함수로 만들고 값은 `encodeURIComponent`로 감싼다.
- 중첩 라우트의 상대 경로는 `toRelativeUnder(base, path)`로 얻는다(직접 문자열을 자르지 않는다).
- 공개 경로를 추가하면 `src/prerender/manifest.ts`와 prerender 검증 스크립트도 함께 갱신한다.

### 선택지: 인증 라우트 (제품마다 다름)

| 제품    | 인증 라우트                                 | 특징                                                                          |
| ------- | ------------------------------------------- | ----------------------------------------------------------------------------- |
| Finance | `/auth` 단일 진입(`AUTH_ROUTE_PATHS.entry`) | `/app/*` 셸 밖에 둬서 하단 내비게이션이 없다. 제공자(Provider) 중립 진입 화면 |
| Carelog | `/auth/{entry,login,signup}` (`AUTH_BASE`)  | 인증 상태에 따라 `Navigate`로 이동                                            |

RPF에는 인증 라우트가 없다. 제품이 필요할 때 위 중 하나를 고르거나 다른 구조를 쓴다. 단 경로 정의는 반드시 `routes.ts`에 둔다.

## 2. 인증 가드

### 규약 (두 제품이 실제로 같은 부분만)

- 인증이 **확정적으로 없는(비로그인)** 상태에서 보호 화면에 들어오면, `routes.ts`에 정의된 인증 진입 경로로 `replace` 이동한다.
- 토큰은 로그·URL·테스트 fixture에 평문으로 남기지 않는다.

### 선택지: 제품별로 다른 부분

| 항목           | Finance                                                                                           | Carelog                                                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 가드 위치      | 라우트(화면)별 `AuthRequiredSurface`                                                              | 보호 영역 경계 한 곳(`ProtectedAppBoundary`)                                                                        |
| 상태 모델      | `unknown` / `guest` / `authenticated` (외부 스토어, `useSyncExternalStore`)                       | bootstrapping / recovering / error / anonymous / authenticated (`AuthProvider` Context + 상태기계 + port + adapter) |
| "확인 중" 처리 | 기본은 보호 화면을 렌더하고, `requireKnownAuthentication`인 화면만 `unknown`에서도 `/auth`로 이동 | 부트스트랩 화면을 보여 주고 확정 전에는 이동하지 않음                                                               |
| 오류 상태      | 별도 상태 없음                                                                                    | `error` 상태와 재시도 화면                                                                                          |

트레이드오프: 경계 한 곳 방식은 상태가 명시적이고 테스트하기 쉽지만 파일·개념이 많아 작은 제품에는 무겁다. 화면별 방식은 가볍지만 가드가 흩어질 수 있다.
추천(참고용): 보호 라우트가 3개 이상이거나 토큰 갱신이 필요하면 경계 방식, 그 미만이면 화면별 방식에서 시작한다. 이 문서는 어느 쪽도 표준으로 정하지 않는다.
공통 인증 상태기계는 RPF에 승격하지 않는다(근거: 평가 문서 3장 "승격하지 않는 것").

### 단일 제품 사례 (승격 근거 부족)

- 로그인 후 이동 경로를 한 함수로 모으는 방식: Carelog `resolvePostAuthPath`. Finance에는 대응 사례가 없다.

## 3. API 호출

### 규약 (두 제품이 실제로 같은 부분만)

- 화면 컴포넌트가 `fetch`를 직접 흩뿌리지 않고 모듈(포트/클라이언트) 뒤에 둔다. 테스트에서 교체 가능해야 한다.
- 요청에 Secret을 하드코딩하지 않는다. 브라우저 번들에 들어가는 `VITE_*` 값은 공개된다고 가정한다.

### 단일 제품 사례 (승격 근거 부족)

- 운영(`import.meta.env.PROD`)에서 `https:`가 아닌 API 베이스 URL을 거부: Carelog `authPort.ts`.
- 오류를 종류가 있는 타입(Error 서브클래스·코드)으로 던져 호출자가 분기: 두 제품 모두 형태는 다르다(Carelog `CarelogHttpError` 등, Finance `FinanceReferenceAuthError` code). 공통 오류 모양은 정하지 않는다.

### 선택지

| 항목                   | 사례                                                                                                                                                                                                                        |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| HTTP 클라이언트        | Carelog는 자체 `createCarelogHttpClient`(401 재시도, 세션 provider, 응답 envelope 처리)를 쓴다. 이는 Carelog API 계약에 묶여 있어 일반화하지 않았다. Finance는 도메인별 포트(Read/Create Port) 뒤에 `fetch` 구현을 주입한다 |
| 데이터 패칭 라이브러리 | 두 제품 모두 사용하지 않는다. 도입은 제품이 정한다(`library-selection.md` 순서 적용)                                                                                                                                        |

RPF는 **공통 API Client를 제공하지 않는다.** 두 제품에 같은 패턴이 없기 때문이다.

## 4. 환경 변수

### 규약 (두 제품이 실제로 같은 부분만)

- 브라우저에 노출할 값만 `VITE_` 접두사를 쓰고, 제품 접두사(`VITE_FINANCE_*`, `VITE_CARELOG_*`)를 붙인다.
- 미설정이면 안전한 기본값(기능 꺼짐 또는 설정 오류)으로 동작한다.
- Secret(토큰·키)은 `VITE_`로 두지 않는다. `.env*` 파일은 커밋하지 않는다.

### 권장안 (Finance 사례, Carelog는 하지 않음)

- `src/vite-env.d.ts`의 `ImportMetaEnv`에 사용하는 `VITE_` 변수를 optional `string`으로 타입 선언한다. Carelog `vite-env.d.ts`에는 선언이 없다.
- 불리언 플래그는 `=== 'true'`로만 켠다(Finance).
- 위험한 플래그는 `PROD`에서 무시한다(Finance: reference auth 활성 여부를 `PROD`와 함께 검사).

### 단일 제품 사례 (승격 근거 부족)

- 값을 한 곳에서 trim·빈 문자열 정규화: Carelog `productionAuthRuntime.ts`. Finance는 여러 파일에서 `import.meta.env`를 직접 읽는다.

### 선택지: 변수 체계

| 제품    | 변수                                                                          | 용도                               |
| ------- | ----------------------------------------------------------------------------- | ---------------------------------- |
| Finance | `VITE_FINANCE_*_ENABLED` 4종(타입 선언됨), DEV 전용 `VITE_LOCAL_*`(선언 없음) | 기능 플래그, 로컬 개발 전용 스위치 |
| Carelog | `VITE_CARELOG_API_BASE_URL`                                                   | API 베이스 URL (+ 운영 https 강제) |

변수 이름은 제품 접두사를 쓴다. 공통 변수 체계는 정하지 않는다.
